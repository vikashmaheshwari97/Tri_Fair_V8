Tri-Fair v8.7: full-coverage research redesign

One proposed method for the paper: Tri-Fair. Internal alias: Tri-Fair-v8.7. Earlier aliases remain available to reproduce previous results. This patch requires the already applied v8.6 efficiency upgrade.

This is a new experimental implementation, not measured evidence of improvement. CPU tests verify mechanics, budget accounting and reproducibility safeguards. No Rocket jobs, model predictions, quality improvements or significance claims were produced by the patch author. The next matched pilot can improve or regress.

What the previous pilot tells us

The 2M efficiency pilot confirmed correct budget reclamation but showed weak Civil Comments and WinoBias generalization. It also showed shared-prompt evaluation discrepancies across batches and duplicated format instructions. Adding more merge/credit mechanisms did not establish consistent gains. The new approach therefore replaces the proposal portfolio and partial-fidelity comparisons with a simpler full-coverage design, rather than adding another unvalidated reward model.

Implemented changes to Tri-Fair

  1. Full search coverage before survival. Reuse the existing NSGA-II environmental selection without modifying its implementation. Every new Tri-Fair candidate is scored across the complete search partition before it competes. This removes partial-versus-full comparison noise, at the cost of fewer cheaply screened candidates.
  2. Measured parent comparisons. Use quality/cost/fairness preferences on measured parents, with a four-percentage-point search-quality eligibility margin. Cached leave-one-block-out ranges guide parent choice only when every compared parent has at least three finite folds. Otherwise all compared parents use pooled values. These are heuristic ranges, not confidence intervals.
  3. Bounded, task-grounded local revisions. A fixed cycle alternates quality repair, fairness repair, gold-demonstration editing, balanced local editing and compression. Generated instructions are limited to 80 words before the shared output contract. There is no learned reward, adaptive operator credit or complementary merge. Invalid/duplicate proposals cannot falsely signal budget exhaustion.
  4. Civil Comments repairs false positives and false negatives separately. Requests include the measured equalized-odds identity gaps (TPR/FPR) as well as cached errors. They distinguish directed abuse/threats from benign identity mentions, quotation, reporting and counterspeech. They preserve the dataset label mapping and successful cases. This is task guidance, not an assurance that quotations or identity mentions are always non-toxic.
  5. Demonstrations stay in the frozen few-shot pool. Initial candidates alternate zero-shot and compact gold examples. WinoBias uses complete pro/anti pairs or no demonstration; instructions retain the pronoun and causal/syntactic evidence.
  6. Idempotent format cleanup. Remove only standalone redundant output instructions; retain conditional label rules and explicit class catalogues. Add one canonical output contract. Output labels remain structured as before.
  7. Repeatability probe before optimization. For the first initial prompt and eight search examples, compare batched, reversed-order and single-example predictions. Invalid labels or disagreements stop the proposed method before search. Save IDs, predictions, instruction hash, hostname and Slurm job ID in repeatability_probe.json. All 24 probe predictions count inside Tri-Fair's downstream cap. Passing this small same-process probe does not establish cross-hardware or universal batch invariance.

Baseline and reporting contract

The NSGA-II, NSGA-III, SPEA2 and Random Search implementation files, objective formulas and frozen-split code are byte-identical to the pre-upgrade files. No method is deliberately weakened. Each method receives the same 2M downstream cap, four initial instructions, maximum two demonstrations, one challenger setting, shared reserve-reclamation protocol and shared final-audit policy. Tri-Fair's generation and initial demonstration allocation are part of the new method and are recorded as such.

Unchanged metrics cannot guarantee dominance: utility, cost and unfairness can trade off. Final shortlist selection stays identical for all methods. Validation is never read by an optimizer, but repeated human inspection of validation during method development means it should not be presented as a fresh unbiased test. Freeze the design before the untouched test split and multi-seed confirmation.

Cost and submission

One seed × four datasets × five methods = 20 optimizer runs, grouped into four Slurm array tasks. Each task runs its five methods sequentially. The downstream ceiling is 40M tokens; meta-generation and held-out evaluation are additional. At concurrency two, two GPU tasks run at once. No GPU job has been submitted by this upgrade.

The new helper can optionally request one GPU family using PILOT_GPU_TYPE=h200-141g (or the configured A100/B200 type). This applies equally to training and validation. The default preserves automatic selection across eligible nodes. A common GPU family improves comparability but does not prove deterministic behavior. The patch does not force vLLM batch-invariant kernels or change installed packages.

If the probe fails

Do not resubmit the expensive matrix repeatedly. Inspect logs/pilot87_JOB_TASK.err and the method's repeatability_probe.json. A failure means the pipeline detected invalid labels or batch/order-sensitive outputs, not that Tri-Fair lost an optimization comparison. Record installed vLLM/torch versions and hardware; resolve it on a small model/backend smoke before training. Forcing a pass or bypassing the probe would not resolve the observed reproducibility problem.
